# Auction ETL database deployment plan

## Objective

Move Auction ETL from the current local PostgreSQL runtime to managed PostgreSQL without losing data or provenance, introducing duplicate identities, running migrations from HTTP requests, or allowing two authoritative ingestion writers.

## Connection separation

### Web runtime

```text
DATABASE_URL=<managed PostgreSQL application connection>
```

### Persistent worker

```text
DATABASE_URL_WORKER=<managed PostgreSQL worker connection>
```

### Migrations

```text
DATABASE_URL_MIGRATIONS=<direct non-pooled PostgreSQL connection>
```

Alembic migrations use the direct migration URL.

Neon provides pooled and direct connection options. Application traffic should use the connection strategy appropriate to its runtime, while schema migration commands use the direct migration connection.

## Database roles

### `auction_app`

Web/control-plane access. No schema DDL.

### `auction_worker`

Ingestion, refresh progress, evidence metadata, and job leasing. No schema DDL.

### `auction_migrator`

Alembic/schema migration role. Its credentials must not be available to normal web requests.

## Job creation

Conceptually:

```text
BEGIN
create queued refresh_job
create waiting Buyee row
create waiting eBay row
create waiting Gripsweat row
COMMIT
```

The web request returns after committing the job. It does not execute marketplace crawling.

## Worker claim

Use transactional row locking:

```sql
BEGIN;

SELECT id
FROM ops.refresh_job
WHERE state = 'queued'
ORDER BY requested_at
FOR UPDATE SKIP LOCKED
LIMIT 1;

UPDATE ops.refresh_job
SET
    state = 'running',
    lease_owner = :worker_id,
    lease_expires_at = :lease_expires_at,
    heartbeat_at = now(),
    started_at = COALESCE(started_at, now()),
    attempt = attempt + 1,
    updated_at = now()
WHERE id = :job_id;

COMMIT;
```

## Lease and heartbeat

Long-running workers periodically refresh:

```text
heartbeat_at
lease_expires_at
updated_at
```

Recovery may requeue an abandoned job only after its lease expires.

## Marketplace progression

Persist:

```text
Buyee running
Buyee done
eBay running
eBay done
Gripsweat running
Gripsweat done
refresh job completed
```

The cloud UI reads these rows rather than parsing machine-local log files.

## Idempotency

Refresh execution IDs are not marketplace identity. Existing marketplace listing uniqueness remains the deduplication boundary, so retrying a failed job must not create duplicate auction identities.

## Staging migration rehearsal

### 1. Record local source state

Capture Alembic revision, schema inventory, table counts, marketplace counts, duplicate identity groups, and reference/evidence counts.

### 2. Create a dump

Template only:

```bash
pg_dump \
    --format=custom \
    --no-owner \
    --no-acl \
    --file auction-etl-precloud.dump \
    "${LOCAL_DATABASE_URL}"
```

### 3. Restore to staging

Template only:

```bash
pg_restore \
    --no-owner \
    --no-acl \
    --clean \
    --if-exists \
    --dbname "${STAGING_DATABASE_URL_DIRECT}" \
    auction-etl-precloud.dump
```

### 4. Apply candidate migrations

Template only:

```bash
DATABASE_URL="${STAGING_DATABASE_URL_DIRECT}" \
python -m alembic upgrade head
```

### 5. Validate staging

Check:

```text
alembic current
auction count
counts by marketplace
duplicate groups
collector review count
reference evidence count
pressing assignments
completeness/history counts
Gripsweat count
foreign-key integrity
```

## Production cutover

1. disable scheduled/background ingestion;
2. wait for active ingestion to reach zero;
3. establish a local write freeze;
4. create a final production manifest and backup;
5. create the final PostgreSQL dump;
6. restore to managed PostgreSQL;
7. run Alembic through the direct migration URL;
8. run read-only parity checks;
9. start the production marketplace worker;
10. verify Buyee profile/authentication;
11. enable the Vercel control plane;
12. run one controlled Latest Refresh;
13. verify counts and marketplace counters;
14. exit maintenance only after acceptance.

## Production acceptance

```text
database connectivity = pass
expected Alembic revision = pass
duplicate identity groups = 0
Buyee owner = healthy
Buyee verifier = pass
Buyee incremental refresh = pass
eBay incremental refresh = pass
Gripsweat incremental refresh = pass
durable refresh job = completed
all marketplace rows = done
UI durable status polling = pass
local subprocess dependency = absent
local refresh-file dependency = absent
```

## Backup policy

Preserve during initial cloud soak:

- final local DB backup;
- source Git commit;
- production tag;
- schema/Alembic revision;
- row-count manifest;
- migration logs;
- acceptance logs.

Do not immediately delete the existing local database. Keep it offline/read-only until cloud production is accepted.

## Rollback

Before cloud writes, stop cloud services and leave validated local production authoritative.

After cloud writes, freeze all writes, compare cloud and local state, determine the authoritative database, and reconcile before redirecting production.

Never perform an automatic destructive reverse migration.

## Preview isolation

Vercel preview deployments should use staging or preview database resources and must not automatically share the production database.

## Migration safety rules

Never:

```text
run Alembic from every web cold start
run migrations from HTTP requests
commit database secrets
use simultaneous local + cloud ingestion writers
skip staging restore rehearsal
destroy the local production copy immediately after cutover
```

## Phase C boundary

Phase C implements the durable coordination layer only:

```text
ops.refresh_job
ops.refresh_marketplace
ops.refresh_event
job service
worker claiming
worker heartbeat
tests
```

Production database migration is not part of Phase C implementation.
